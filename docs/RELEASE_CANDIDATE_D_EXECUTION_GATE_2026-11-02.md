## 2. Exact offline interoperability gate

Use an existing **local Git clone** containing both pinned commits. Read both
commits without changing `main`, `develop-v0.3.0`, or the source dataset.
No Git fetch, network, package installation, private user data, or uploaded
research material is needed.

1. Export the two pinned Git trees into separate temporary directories with
   `git archive <full-commit-SHA>`. Verify each commit with
   `git rev-parse <SHA>^{commit}` first. Do not extract untrusted tar links.
2. Run each CLI in a separate Python subprocess with `PYTHONPATH` set to that
   exported tree's `src` directory, using
   `python -c 'from labvault_scout.cli import main; main()' <command>`.
   Verify that the stable CLI identifies itself as `0.3.2`.
3. Generate **actual stable** scan reports for an empty synthetic directory,
   an ordinary CSV, and a CSV plus a newly added text file. Record the
   generated `scan.json` SHA-256 and summary counts.
4. Run development `verify --json` on the actual stable reports, then
   development `verify-bundle --json` on the stable bundle and development
   `compare` on two stable reports. Record exact exit codes and statuses.
5. Produce a stable `comparison.json` and stable `verify --json` output.
   Check them against the development packaged comparison and verification
   JSON Schemas in a separate, explicit schema-validator run. Do not equate
   structural inspection with JSON Schema validation.
6. On POSIX only, scan a synthetic file literally named `C:sample.csv`
   using stable v0.3.2. Record whether development rejects its actual
   stable-generated report. Classify that rejection as the known C-01
   intentional compatibility break, not as an ordinary-case PASS.
7. Compare pre-scan and post-scan source bytes and timestamps. Save the
   Python version, platform, both full commit SHAs, all command exit codes,
   generated report hashes, and any failures in a machine-readable record.

The environment executing this gate must have the local Git objects.
Until it is executed, historical interoperability remains **UNVERIFIED**.

## 4. Candidate version policy for owner review

Two defensible paths remain. `0.3.3rc1` is appropriate only if the owner
accepts a patch-level release with a documented, narrow security-related
compatibility break. `0.4.0rc1` more clearly communicates the tightened
schema-1 acceptance contract and is preferable if consumers rely on the old
report acceptance behavior. Neither candidate number is selected or adopted
by this document. A release request must explicitly state the selected
version, the C-01 behavior, and remaining evidence limitations.

## 5. Stop conditions

Any failed current CI job blocks additional code commits until that failure
is diagnosed and a full six-job rerun succeeds. A new reproducible integrity
or source-safety blocker reopens the relevant bounded gate. Otherwise,
avoid additional synthetic boundary enumeration and focus on D-C01 through
D-FREEZE. No main changes, PR merges, or GitHub Releases are authorized.
